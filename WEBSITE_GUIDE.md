# Website Guide for paramo.sh

This guide explains how the Páramo website is built, published, and maintained. It is written for someone who is not a software engineer, so it uses plain English and names the exact files where important things live.

## 1. What the site is built with

The site is built with Next.js, a website framework for React. The project uses the older Next.js pages system, not the newer application folder system.

Main stack:

- Framework: Next.js. The requested version in `package.json` is `^16.1.6`, and the locked version in `package-lock.json` is `16.1.6`.
- Language: TypeScript for most site code, with one JavaScript data file at `src/data/flashcards.js`.
- User interface library: React. The requested version in `package.json` is `^19.0.0`, and the locked version in `package-lock.json` is `19.2.4`.
- Styling approach: regular cascading style sheets in `src/styles/globals.css`, page-specific cascading style sheets in `src/styles/architect-prep.css`, and a large block of page-specific styling inside `src/pages/index.tsx`.
- Component library: there is no broad design component library. The only external site helper is `@hacktoolkit/nextjs-htk`, used for Google Analytics in `src/pages/_app.tsx`.

Where the pages live:

- The homepage lives in `src/pages/index.tsx`.
- The hidden Architect Prep flashcard page lives in `src/pages/architect-prep.tsx`.
- The blog listing page lives in `src/pages/blog/index.tsx`.
- Each blog article page is generated by `src/pages/blog/[slug].tsx`.
- The case studies listing page lives in `src/pages/case-studies/index.tsx`.
- Each case study page is generated by `src/pages/case-studies/[slug].tsx`.
- There is no custom not found page file. The not found page is generated by Next.js because there is no `src/pages/404.tsx`.

Where shared pieces live:

- Shared navigation for blog and case study pages lives in `src/components/Nav.tsx`.
- Shared footer for blog and case study pages lives in `src/components/Footer.tsx`.
- Structured search data lives in `src/components/StructuredData.tsx`.
- Scroll reveal behavior lives in `src/components/ScrollReveal.tsx`.
- Global site settings live in `src/config/site.ts`.
- The homepage has its own navigation, footer, and most of its own styling inside `src/pages/index.tsx`, so it does not fully share the same navigation and footer files used by the blog and case study pages.

Where images and other assets live:

- Source assets live in `public/`.
- Logos, marks, and favicons live in `public/assets/`.
- The open graph sharing image lives at `public/og-image.png`.
- The custom domain file lives at `public/CNAME`.
- Search crawler files live at `public/robots.txt`, `public/llms.txt`, and `public/llms-full.txt`.
- Google site verification lives at `public/googlec4309e858071aca0.html`.
- Published copies of these files are generated into `docs/` when the site is built.

Content systems and data files:

- There is no headless content management system.
- There is no Markdown content system.
- Blog article metadata lives in `src/data/blog-posts.ts`.
- Some full blog article content also lives inside `src/data/blog-posts.ts` as Hypertext Markup Language strings.
- Case study metadata lives in `src/data/case-studies.ts`.
- Full case study content lives in `src/content/case-studies/*.html`.
- The Architect Prep flashcards live in `src/data/flashcards.js`.
- The sitemap is generated from `src/scripts/generate-sitemap.ts`.

## 2. How it gets published

The site is hosted on GitHub Pages.

How I know:

- The GitHub repository is `ParamoAI/paramo.sh`.
- GitHub Pages reports that the site is built, public, and served from the `main` branch using the `/docs` folder.
- `public/CNAME` and `docs/CNAME` both contain `paramo.sh`.
- The live site response headers say `server: GitHub.com`.
- `next.config.mjs` sets `output: 'export'` and `distDir: 'docs'`, which means the Next.js site is exported as static files into the `docs/` folder for GitHub Pages.

What triggers deployment:

- A push to the `main` branch triggers the GitHub Actions workflow in `.github/workflows/ci.yml`.
- GitHub Pages is configured to publish from `main` and `/docs`.
- Pull requests run the same build check, but this repository does not show automatic live preview links for pull requests.
- The latest observed main branch build took about 40 seconds for the build check and about 33 seconds for the GitHub Pages deployment.
- Build logs are visible in GitHub Actions for the repository. The current workflow file is `.github/workflows/ci.yml`.

Build command and output folder:

- The main build command in `package.json` is `npm run build`.
- That command runs `next build`, touches `docs/.nojekyll`, and runs `tsx src/scripts/generate-sitemap.ts`.
- The Makefile target `make build` cleans the old build, installs dependencies, runs the build, copies `CNAME` into `docs/`, and touches `docs/.nojekyll`.
- The published output folder is `docs/`.
- The source configuration file for this is `next.config.mjs`.

Host configuration files:

- GitHub Pages domain file: `public/CNAME`.
- Published domain file: `docs/CNAME`.
- GitHub Actions workflow: `.github/workflows/ci.yml`.
- Next.js export settings: `next.config.mjs`.
- There is no `netlify.toml`.
- There is no `wrangler.toml`.
- There is no `vercel.json`.
- There is no `_redirects` file.
- There is no `_headers` file.

Environment variables and secrets:

- I did not find any `.env` files in the repository.
- I did not find code using `process.env`.
- The build does not appear to need environment variables or secrets.
- Google Analytics measurement identifiers are hardcoded in `src/config/site.ts`.

## 4. How to add a new page, step by step

To add a normal new page:

1. Create a new file in `src/pages/`.
2. For a page at `https://paramo.sh/example/`, create `src/pages/example.tsx`.
3. Start the file from an existing page that is closest to what you need. For a simple marketing page, `src/pages/blog/index.tsx` or `src/pages/case-studies/index.tsx` is easier to copy than the homepage.
4. Add the page title, description, canonical address, open graph fields, and Twitter sharing fields inside the page's `<Head>` block.
5. If the page should appear in the shared navigation, edit `src/components/Nav.tsx`.
6. If the page should appear in the shared footer, edit `src/components/Footer.tsx`.
7. If the page should appear in the homepage navigation or homepage footer, edit `src/pages/index.tsx`, because the homepage uses its own navigation and footer.
8. If the page should appear in search engines, add it to the `pages` array in `src/scripts/generate-sitemap.ts`.
9. Run `npm ci` if dependencies are not installed.
10. Run `npm run dev` to preview locally.
11. Run `npm run build` or `make build` before opening a pull request.
12. Open a pull request into `main`.
13. After the pull request is approved and merged, confirm the live page at `https://paramo.sh/example/`.

Common things that break for a new page:

- Forgetting to add the page to `src/scripts/generate-sitemap.ts`, which means search engines may not discover it through the sitemap.
- Forgetting to add a page title and description in the `<Head>` block.
- Linking to images without placing them in `public/`.
- Using an image path without a leading slash. Public assets should usually be linked like `/assets/logo-v7.png`.
- Editing the generated `docs/` files by hand. Those files should come from the build.
- Updating only `src/components/Nav.tsx` and forgetting that the homepage has a separate navigation inside `src/pages/index.tsx`.

To add a new blog post:

1. Add a new item to the `blogPosts` array in `src/data/blog-posts.ts`.
2. Required fields are `slug`, `title`, `description`, `tag`, `date`, `readTime`, and `author`.
3. The `slug` becomes the address. A slug of `my-new-post` becomes `https://paramo.sh/blog/my-new-post/`.
4. Add full article content in the optional `contentHtml` field if the article should be complete at launch.
5. If `contentHtml` is missing, the page still publishes, but it shows placeholder text that says the full article is coming soon.
6. Run `npm run build` or `make build`.
7. Confirm the article appears on `https://paramo.sh/blog/` and opens at its own address.

Common blog post problems:

- Missing `contentHtml` creates a live placeholder article.
- An invalid `date` can weaken article structured data.
- The current content approach stores full article Hypertext Markup Language inside a TypeScript data file, which is awkward for writing and review.
- Some older article text links to a different Calendly address than the current one in `src/config/site.ts`.

To add a new case study:

1. Add a new item to the `caseStudies` array in `src/data/case-studies.ts`.
2. Required fields are `slug`, `industry`, `industryEmoji`, `stat`, `title`, `avatar`, `name`, and `role`.
3. The `slug` becomes the address. A slug of `my-case-study` becomes `https://paramo.sh/case-studies/my-case-study/`.
4. Add the full case study content as a Hypertext Markup Language file in `src/content/case-studies/`.
5. The content file name must match the slug. For example, `my-case-study` needs `src/content/case-studies/my-case-study.html`.
6. If the content file is missing, the page still publishes, but it shows placeholder text that says the full case study content is coming soon.
7. Run `npm run build` or `make build`.
8. Confirm the case study appears on `https://paramo.sh/case-studies/` and opens at its own address.

Common case study problems:

- The data entry and content file must use the same slug.
- The dynamic case study page strips outer wrappers from the content file in `src/pages/case-studies/[slug].tsx`, so copied Hypertext Markup Language needs to match the expected shape.
- There is a duplicated code comment in `src/pages/case-studies/[slug].tsx` near the content wrapper stripping logic.

## 7. Health check

Dependency age and security:

- `npm outdated --json` reports these packages can move forward within their allowed version ranges:
  - `next`: current lock is `16.1.6`; available wanted and latest version is `16.4.0`.
  - `react`: current lock is `19.2.4`; available wanted and latest version is `19.3.0`.
  - `react-dom`: current lock is `19.2.4`; available wanted and latest version is `19.3.0`.
  - `@hacktoolkit/nextjs-htk`: current lock is `0.2.0`; latest version is `0.3.0`.
- `npm audit --omit=dev --json` reports 8 production dependency vulnerabilities:
  - 1 critical vulnerability.
  - 6 high vulnerabilities.
  - 1 moderate vulnerability.
- The most important finding is that `next` is flagged through multiple advisories, including critical advisories. Updating Next.js should be a priority.
- Other flagged packages include `immutable`, `nanoid`, `picomatch`, `postcss`, `sharp`, `source-map-js`, and `baseline-browser-mapping`.

Broken links and missing images:

- I checked generated Hypertext Markup Language files in `docs/`.
- I did not find missing local image files in the generated pages.
- I did find a repeated broken anchor: `src/components/Nav.tsx` links "Services" to `/#offers`, but the current homepage in `src/pages/index.tsx` does not contain an `id="offers"` section.
- That broken anchor appears on the blog and case study pages because they use `src/components/Nav.tsx`.
- `www.paramo.sh` does not resolve, which is a domain-level gap if people try to visit the world wide web version of the address.

Titles and descriptions:

- The main generated content pages have titles and descriptions.
- The dynamically generated blog article pages get their titles and descriptions from `src/data/blog-posts.ts`.
- The dynamically generated case study pages get their titles and descriptions from `src/data/case-studies.ts`.
- The Architect Prep page has a title and description but is not in the sitemap.

What makes a redesign harder:

- The homepage uses a different navigation and footer than the rest of the site.
- The homepage styling is mostly embedded directly inside `src/pages/index.tsx`, while the rest of the site uses `src/styles/globals.css`.
- Blog content is partly inside TypeScript strings, which makes writing, editing, and review harder than a Markdown or content management system workflow.
- Four blog pages are published as placeholders, so a redesign would need content cleanup, not only visual cleanup.
- Analytics is wired in two places, which should be simplified before a redesign launch.
- The shared navigation has a stale link to a removed homepage section.
- The published `docs/` folder is committed to the repository, so agents need to be careful not to hand-edit generated files.

What I would change first:

1. Update dependencies, especially Next.js, and rerun the audit.
2. Fix the stale `/#offers` navigation link in `src/components/Nav.tsx`.
3. Decide whether `architect-prep` belongs on the public site. If yes, add it to navigation and the sitemap. If no, remove it from production.
4. Connect or remove the homepage sample report form, because it currently gives users a success message without sending anything.
5. Move homepage navigation, footer, and styling toward shared components so a redesign can be applied consistently.
6. Move blog content out of TypeScript strings into a cleaner writing system, such as Markdown or a small content collection.

## 8. How another artificial intelligence agent should work in this repo

Branch and pull request rules:

- Work from `main`.
- Create a feature branch before making changes.
- Never push directly to `main`.
- Open a pull request into `main`.
- Never merge your own pull request.
- For visual changes, attach screenshots to the pull request and post screenshots in `#cc-website` for operator review before merge.

How to run the site locally:

1. Run `npm ci`.
2. Run `npm run dev`.
3. Open `http://localhost:3000`.
4. If port 3000 is already used, Next.js will usually offer another port. Use the address it prints.

How to preview a change before it goes live:

1. Run `npm run dev` for a local preview while editing.
2. Run `npm run build` or `make build` before opening the pull request.
3. Review the generated site locally from the development server or by checking the built `docs/` output.
4. Open a pull request and wait for the GitHub Actions build check.
5. After merge, GitHub Pages publishes from `main` and `/docs`.
6. Confirm the live change at `https://paramo.sh/`.

What another agent should never touch without a specific reason:

- Do not push directly to `main`.
- Do not run `make deploy`; the repository instructions say deploy is admin-only.
- Do not hand-edit `docs/` for normal source changes. Build output should come from `src/` and `public/`.
- Do not print secret values. This site currently does not need build secrets.
- Do not change the domain file `public/CNAME` unless the domain is intentionally changing.
- Do not remove `docs/.nojekyll`; GitHub Pages needs it for files under `_next/`.
- Do not change analytics identifiers casually. They live in `src/config/site.ts`.
- Do not assume the homepage and the rest of the site share the same navigation or footer. Check both `src/pages/index.tsx` and `src/components/Nav.tsx` or `src/components/Footer.tsx`.
- Do not report website work as done until it is merged, deployed, and verified live. If it is only on a branch or in a pull request, say that clearly.
